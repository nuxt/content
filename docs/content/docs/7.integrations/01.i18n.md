Nuxt Content works with `@nuxtjs/i18n` to build multi-language websites. Add the `i18n` option to a collection to keep every locale in one collection: queries return the content of the active locale and fall back to the default locale for content that has no translation yet.

## Setup

::prose-steps
### Install the module

```bash [terminal]
npm install @nuxtjs/i18n
```

### Configure your `nuxt.config.ts`

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['@nuxt/content', '@nuxtjs/i18n'],
  i18n: {
    locales: [
      { code: 'en', name: 'English', language: 'en-US' },
      { code: 'fr', name: 'French', language: 'fr-FR' },
      { code: 'de', name: 'German', language: 'de-DE' },
    ],
    strategy: 'prefix_except_default',
    defaultLocale: 'en',
  },
})
```

### Enable i18n on your collections

```ts [content.config.ts]
import { defineCollection, defineContentConfig } from '@nuxt/content'
import { z } from 'zod'

export default defineContentConfig({
  collections: {
    // Reads `locales` and `defaultLocale` from @nuxtjs/i18n
    docs: defineCollection({
      type: 'page',
      source: '*/docs/**',
      i18n: true,
    }),
    team: defineCollection({
      type: 'data',
      source: 'team/*.yml',
      schema: z.object({
        name: z.string(),
        role: z.string(),
        country: z.string(),
      }),
      i18n: {
        locales: ['en', 'fr', 'de'],
        defaultLocale: 'en',
      },
    }),
  },
})
```

Pass an object instead of `true` to set the locales yourself, for example when another layer configures `@nuxtjs/i18n`. Each i18n collection gets a `locale` column and an index on `(locale, stem)`.
::

## Content Structure

You can keep each translation in its own file, translate fields inline, or mix both approaches in one collection.

### Locale Directories

Put each translation in a directory named after its locale:

```text
content/
  en/
    docs/
      getting-started.md
  fr/
    docs/
      getting-started.md
```

Nuxt Content stores the locale in the `locale` column and removes the locale directory from `path` and `stem`. Both files above get `path: /docs/getting-started` and `stem: docs/getting-started`, which links them as translations of each other.

The locale directory can also come right after the fixed directory of the source, such as `content/docs/fr/getting-started.md` with `source: 'docs/**'`. Directory names match locale codes case-insensitively, so a `pt-br` directory belongs to the `pt-BR` locale. Files outside a locale directory belong to the default locale.

### Inline Translations

Add an `i18n` section to translate some fields of a file and keep the rest:

```yaml [content/team/jane.yml]
name: Jane Doe
role: Developer
country: Switzerland

i18n:
  fr:
    role: Développeuse
    country: Suisse
  de:
    role: Entwicklerin
    country: Schweiz
```

The top-level values belong to the locale of the file, the default locale here, and fill in every field a translation leaves out. Inline translations follow these rules:

- Nested objects merge field by field. Arrays of objects merge by index, so item fields you do not translate, such as links or icons, keep their values. Arrays of plain values replace the original array.
- Fields outside the collection schema translate into `meta`, where Nuxt Content stores them.
- `id`, `stem`, `path`, `locale` and `extension` cannot be translated. A block for the file's own locale is ignored and logs a warning.
- An empty block such as `fr:` is a placeholder. Queries in that locale fall back to the default locale.

In Markdown files, the front matter can hold an `i18n` section to translate fields such as `title` and `description`. The body cannot be translated inline, so use a file per locale for pages with translated text. In page collections, `seo.title` and `seo.description` follow the translated `title` and `description` unless you set them yourself.

CSV files cannot hold inline translations. See [CSV](/docs/files/csv#i18n) for the alternative.

::warning
Do not declare a field named `i18n` in the collection schema. Nuxt Content would store it as data instead of expanding the translations.
::

## Querying Content

### Pages and Components

In Vue, `queryCollection` uses the active locale of `@nuxtjs/i18n`, during server-side rendering and on the client. Content paths have no locale prefix, so remove the prefix from the route path, and add the locale to the `useAsyncData` key to fetch the content again after a locale switch:

```vue [pages/[...slug\\].vue]
<script setup lang="ts">
const route = useRoute()
const { locale } = useI18n()

const path = computed(() => route.path.replace(new RegExp(`^/${locale.value}(?=/|$)`), '') || '/')

const { data: page } = await useAsyncData(
  () => `page:${locale.value}:${path.value}`,
  () => queryCollection('docs').path(path.value).first(),
)
</script>

<template>
  <ContentRenderer v-if="page" :value="page" />
</template>
```

In the default locale, queries return content of the default locale. In another locale, each item comes in the active locale when a translation exists and in the default locale otherwise:

- Filters apply to the chosen translation. A French page with `navigation: false` stays out of the French navigation, even when the English page is in the navigation.
- `order()`, `skip()`, `limit()` and `count()` work the same way as in a query without fallback.

`queryCollectionNavigation`, `queryCollectionItemSurroundings`, `queryCollectionSearchSections` and `useSearchCollection` also use the active locale. `useSearchCollection` rebuilds its index after a locale switch.

### Explicit Locale

Call `.locale()` to choose the locale yourself. Pass a fallback locale to fill in content without translation:

```ts
// French content only
queryCollection('docs').locale('fr').all()

// French content, English where no French translation exists
queryCollection('docs').locale('fr', { fallback: 'en' }).all()
```

The navigation, surroundings and search sections helpers accept `.locale()` too. A filter on the `locale` column, such as `.where('locale', '=', 'fr')`, also turns off the active locale.

### Server Routes

Server queries return content of every locale until you call `.locale()`, since `@nuxtjs/i18n` does not expose the locale of a request to server routes. Resolve the locale in your handler, for example with your [locale detector](https://i18n.nuxtjs.org/docs/guide/server-side-translations):

```ts [server/api/posts.get.ts]
import localeDetector from '~~/i18n/localeDetector'

export default defineEventHandler(async (event) => {
  const locale = localeDetector(event, { defaultLocale: 'en', fallbackLocale: 'en' })

  return queryCollection(event, 'posts').locale(locale, { fallback: 'en' }).all()
})
```

### Language Switcher

Use [`queryCollectionLocales`](/docs/utils/query-collection-locales) to list the translations of a page, for a language switcher or `hreflang` links. The returned paths have no locale prefix, so pass them to `useLocalePath()`.

## Translation Tracking

Each inline translation stores `meta._i18nSourceHash`, a hash of the default values it translates. The hash changes when one of these values changes, so a tool that saves the hash of a reviewed translation can flag the translation as outdated. Translations in locale directories have no hash.

```ts
const member = await queryCollection('team').locale('fr').first()
console.log(member?.meta._i18nSourceHash)
```

## Limitations

- **Translated slugs**: translations are linked by their stem, so files need the same name in every locale directory. `en/products.md` and `de/produkte.md` are two different items. Translated routes depend on `@nuxtjs/i18n`, see [nuxt-modules/i18n#3028](https://github.com/nuxt-modules/i18n/discussions/3028).
- **Locale codes**: the active locale only applies when it is one of the collection locales. With `en-US` in `@nuxtjs/i18n` and `en` in the collection, queries return content of every locale and log a warning in development.
- **Nuxt Studio**: Nuxt Studio does not support i18n collections yet. Its file tree follows the locale of the site, and edits only get their locale after the next build.
- **Preview API**: the legacy preview API (`content.preview.api`) does not support i18n collections.
