Nuxt Content works with `@nuxtjs/i18n` to build multi-language websites. Add the `i18n` option to a collection to keep every locale in one collection: queries return the content of the active locale and fall back to the default locale for content that has no translation yet.

## Setup

::prose-steps
### Install the module

```bash [terminal]
npm install @nuxtjs/i18n
```

### Configure your `nuxt.config.ts`

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['@nuxt/content', '@nuxtjs/i18n'],
  i18n: {
    locales: [
      { code: 'en', name: 'English', language: 'en-US' },
      { code: 'fr', name: 'French', language: 'fr-FR' },
      { code: 'de', name: 'German', language: 'de-DE' },
    ],
    strategy: 'prefix_except_default',
    defaultLocale: 'en',
  },
})
```

### Enable i18n on your collections

```ts [content.config.ts]
import { defineCollection, defineContentConfig } from '@nuxt/content'
import { z } from 'zod'

export default defineContentConfig({
  collections: {
    // Reads `locales` and `defaultLocale` from @nuxtjs/i18n
    docs: defineCollection({
      type: 'page',
      source: '*/docs/**',
      i18n: true,
    }),
    team: defineCollection({
      type: 'data',
      source: 'team/*.yml',
      schema: z.object({
        name: z.string(),
        role: z.string(),
        country: z.string(),
      }),
      i18n: {
        locales: ['en', 'fr', 'de'],
        defaultLocale: 'en',
      },
    }),
  },
})
```

Pass an object instead of `true` to set the locales yourself, for example when another module adds locales to `@nuxtjs/i18n` through `moduleDependencies` or the `i18n:registerModule` hook. Each i18n collection gets a `locale` column and an index on `(stem, locale)`. Add an [index](/docs/collections/define#database-indexes) on `path` to large collections, since pages are queried by path.
::

## Content Structure

You can keep each translation in its own file, translate fields inline, or mix both approaches in one collection.

### Locale Directories

Put each translation in a directory named after its locale:

```text
content/
  en/
    docs/
      getting-started.md
  fr/
    docs/
      getting-started.md
```

Nuxt Content stores the locale in the `locale` column and removes the locale directory from `path` and `stem`. Both files above get `path: /docs/getting-started` and `stem: docs/getting-started`, which links them as translations of each other.

The locale directory can also come right after the fixed directory of the source, such as `content/docs/fr/getting-started.md` with `source: 'docs/**'`. Directory names match locale codes case-insensitively, so a `pt-br` directory belongs to the `pt-BR` locale. Files outside a locale directory belong to the default locale, and so do files of a source whose custom `prefix` leaves out the locale directory, such as `{ include: 'fr/**', prefix: '' }`. A top-level `locale` field, set to one of the collection locales, sets the locale of a file instead of its directory. Other values are ignored with a warning.

### Inline Translations

Add an `i18n` section to translate some fields of a file and keep the rest:

```yaml [content/team/jane.yml]
name: Jane Doe
role: Developer
country: Switzerland

i18n:
  fr:
    role: Développeuse
    country: Suisse
  de:
    role: Entwicklerin
    country: Schweiz
```

The top-level values belong to the locale of the file, the default locale here, and fill in every field a translation leaves out. Inline translations follow these rules:

- Locale keys match the collection locales case-insensitively, like locale directories.
- Nested objects merge field by field. Arrays of objects merge by index, so item fields you do not translate, such as links or icons, keep their values. Arrays of plain values replace the original array.
- Fields outside the collection schema translate into `meta`, where Nuxt Content stores them.
- `id`, `stem`, `path`, `locale` and `extension` cannot be translated. A block for the file's own locale is ignored, with a warning when its values differ from the top-level values.
- A block without translatable fields, such as `fr:` or `fr: {}`, is a placeholder. Queries in that locale fall back to the default locale.

In Markdown files, the front matter can hold an `i18n` section to translate fields such as `title` and `description`. The body cannot be translated inline, so use a file per locale for pages with translated text. In collections with a `seo` field, such as page collections, `seo.title` and `seo.description` follow the translated `title` and `description` unless you set them yourself.

CSV files cannot hold inline translations. See [CSV](/docs/files/csv#i18n) for the alternative.

The [`content:file:afterParse`](/docs/advanced/hooks) hook runs once per file, before Nuxt Content builds the translations. A hook that adds a translatable value can set it in `content.meta.i18n[locale]` as well.

::warning
Do not declare a field named `i18n` in the collection schema. Nuxt Content would store it as data instead of expanding the translations.
::

## Querying Content

### Pages and Components

In Vue, `queryCollection` uses the active locale of `@nuxtjs/i18n`, during server-side rendering and on the client. Content paths have no locale prefix, so build the path from the route parameters, which leave the prefix out. Add the locale to the `useAsyncData` key, so that Nuxt fetches the content again after a locale switch and `nuxi generate` does not share it between pages of different locales:

```vue [pages/[...slug\\].vue]
<script setup lang="ts">
const route = useRoute()
const { locale } = useI18n()

const path = computed(() => `/${[route.params.slug ?? []].flat().join('/')}`)

const { data: page } = await useAsyncData(
  () => `page:${locale.value}:${path.value}`,
  () => queryCollection('docs').path(path.value).first(),
)
</script>

<template>
  <ContentRenderer v-if="page" :value="page" />
</template>
```

In the default locale, queries return content of the default locale. In another locale, each item comes in the active locale when a translation exists and in the default locale otherwise:

- Filters apply to the chosen translation. A French page with `navigation: false` stays out of the French navigation, even when the English page is in the navigation.
- `order()`, `skip()`, `limit()` and `count()` work the same way as in a query without fallback.
- Content falls back to the default locale of the collection. A `fallbackLocale` chain in the vue-i18n options only applies to messages.

`queryCollectionNavigation`, `queryCollectionItemSurroundings`, `queryCollectionSearchSections` and `useSearchCollection` also use the active locale. Add the locale to the keys of `useAsyncData` calls that use them:

```ts
const { data: navigation } = await useAsyncData(
  () => `navigation:${locale.value}`,
  () => queryCollectionNavigation('docs'),
)
```

`useSearchCollection` rebuilds its index after a locale switch.

::warning
A query reads the active locale when you create it. During server-side rendering, the Nuxt context is only available until the first `await` in a `useAsyncData` handler, so a query created after it cannot read the locale and returns every locale. Create the query before that `await`, or run it with the `nuxtApp` that the handler receives:

```ts
const { data } = await useAsyncData(() => `page:${locale.value}:${path.value}`, async (nuxtApp) => {
  const page = await queryCollection('docs').path(path.value).first()
  const surround = await nuxtApp.runWithContext(() => queryCollectionItemSurroundings('docs', path.value))
  return { page, surround }
})
```
::

With the `skipSettingLocaleOnNavigate` option of `@nuxtjs/i18n`, the active locale changes after the next page has loaded its data. Read the locale from the route in that case, and pass it to `.locale()` with the default locale as fallback.

### Explicit Locale

Call `.locale()` to choose the locale yourself. Without `@nuxtjs/i18n`, queries return every locale until you call it. Pass a fallback locale to fill in content without translation:

```ts
// French content only
queryCollection('docs').locale('fr').all()

// French content, English where no French translation exists
queryCollection('docs').locale('fr', { fallback: 'en' }).all()
```

The navigation, surroundings and search sections helpers accept `.locale()` too. A filter on the `locale` column, such as `.where('locale', '=', 'fr')`, also turns off the active locale.

### Server Routes

Server queries return content of every locale until you call `.locale()`, since `@nuxtjs/i18n` does not expose the locale of a request to server routes. Send the locale of the page to the route, and pass it to `.locale()` when it is one of the collection locales:

```ts [server/api/posts.get.ts]
const locales = ['en', 'fr', 'de']

export default defineEventHandler(async (event) => {
  const { locale } = getQuery(event)
  const code = typeof locale === 'string' && locales.includes(locale) ? locale : 'en'

  return queryCollection(event, 'posts').locale(code, { fallback: 'en' }).all()
})
```

```vue [pages/posts.vue]
<script setup lang="ts">
const { locale } = useI18n()

const { data: posts } = await useFetch('/api/posts', { query: { locale } })
</script>
```

A [locale detector](https://i18n.nuxtjs.org/docs/guide/server-side-translations) reads the locale from the request instead: the query, a cookie or the `Accept-Language` header. Requests without them, such as prerendering and crawlers, get the default locale.

### Language Switcher

Content paths are the same in every locale, so the links of `useSwitchLocalePath()` already open the translated page, or the default locale content when no translation exists. Use [`queryCollectionLocales`](/docs/utils/query-collection-locales) to list only the translations a page has, for a language switcher or `hreflang` links. The returned paths have no locale prefix, so pass them to `useLocalePath()`.

## Translation Tracking

Each inline translation stores `meta._i18nSourceHash`, a hash of the top-level values it translates. The hash changes when one of these values changes, so a tool that saves the hash of a reviewed translation can flag the translation as outdated. Translations in locale directories have no hash.

```ts
const member = await queryCollection('team').locale('fr').first()
console.log(member?.meta._i18nSourceHash)
```

## Limitations

- **Translated slugs**: translations are linked by their stem, so files need the same name in every locale directory. `en/products.md` and `de/produkte.md` are two different items. Translated routes depend on `@nuxtjs/i18n`, see [nuxt-modules/i18n#3028](https://github.com/nuxt-modules/i18n/discussions/3028).
- **Locale codes**: the active locale only applies when it is one of the collection locales. Otherwise queries return the default locale and log a warning in development, for example in a collection translated into fewer locales than the site, or with `en-US` in `@nuxtjs/i18n` and `en` in the collection.
- **Nuxt Studio**: Nuxt Studio does not support i18n collections yet. Its file tree follows the locale of the site, and edits only get their locale after the next build.
- **Preview API**: the legacy preview API (`content.preview.api`) does not support i18n collections.
- **Client-side queries**: the first query in the browser downloads the content of every locale of an i18n collection. Sites with many locales or large collections can use [separate collections per locale](#separate-collections-per-locale).
- **LLMs integration**: `llms.txt` and `llms-full.txt` contain the default locale of i18n collections unless a section filters on `locale`. Links to translations start with their locale, for example `/raw/fr/docs/getting-started.md`.
